# بوابات الدفع الإلكتروني — عالم البكلاوه

كل شيء يُضبط من **لوحة الإدارة ← بوابات الدفع**؛ لا تعديل كود ولا متغيرات بيئة. تضيف بوابة، تُدخل مفاتيحها، تفعّلها فتظهر للعملاء في صفحة إتمام الطلب.

## ما يضمنه النظام (مهما كانت البوابة)

| الضمان | كيف |
|---|---|
| لا نخزّن بيانات البطاقات | العميل يُحوَّل إلى صفحة الدفع لدى البوابة |
| المفاتيح لا تصل للمتصفح | تُحفظ مشفّرة (AES‑256‑GCM) في قاعدة البيانات ولا تُعاد من الـ API (تظهر `••••xyz` فقط) |
| «تم الدفع» لا تُعرض إلا بعد تأكيد حقيقي | توقيع Webhook / توقيع استعلام العودة / استعلام من الخادم للبوابة، **وليس** بما يقوله المتصفح |
| مطابقة المبلغ | مبلغ البوابة يجب أن يساوي إجمالي الطلب وإلا تُوسَم العملية «فشل» وتحتاج مراجعة |
| لا تكرار | كل حدث Webhook يُسجَّل بمعرّفه، وتكراره لا يغيّر شيئًا؛ ومحاولة الدفع المعلّقة تُعاد استخدامها عند الضغط المزدوج |
| حماية SSRF | عناوين البوابة يجب أن تكون https وعامة (تُرفض الشبكات الداخلية وlocalhost وعناوين الـ metadata) |
| فشل/إلغاء | يبقى الطلب «غير مدفوع» ويُعرض زر «إعادة محاولة الدفع» في صفحة الطلب |

مفتاح التشفير: متغير `APP_SECRET` (32 حرفًا فأكثر) أو، إن لم يُضبط، ملف `DATA_DIR/.secret` يُنشأ تلقائيًا بصلاحية 600. **احتفظ بنسخة احتياطية منه مع قاعدة البيانات**؛ فقدانه يعني إعادة إدخال مفاتيح البوابات.

## النوع 1: Plutu (بوابات ليبية)

يدعم: بطاقات مصرفية ليبية (`localbankcards`) · بطاقات دولية MPGS (`mpgs`) · Tlync (محافظ/تداول/سداد…).

تحتاج حساب تاجر لدى Plutu ثم تُدخل: **API Key** و**Access Token** و**Secret Key**.

العقد الذي ينفّذه النظام (مأخوذ من SDK العام لـ Plutu):

- `POST {base_url}/transaction/{gateway}/confirm` بترويسات `X-API-KEY` و`Authorization: Bearer <Access Token>`.
- الجسم: `amount` (بالدينار) و`invoice_no` (= رقم الطلب‑رقم المحاولة، مثل `ABK-1001-1`) و`return_url` و`lang`، ومع Tlync: `mobile_number` و`callback_url`.
- الرد: `result.redirect_url` و`result.transaction_id` ← يُحوَّل العميل إلى `redirect_url`.
- عند العودة (GET) وعند Callback الـ Tlync (POST) تصل `approved` و`canceled` و`invoice_no` و`amount` و`transaction_id` و`hashed`؛ نتحقق من `hashed = HMAC‑SHA256(Secret Key, "k=v&k=v…")` بحروف كبيرة. توقيع غير صحيح ← يُتجاهل تمامًا.

> ⚠️ **لم تُجرَّب هذه البوابة على حساب تاجر حقيقي** (لا أملك مفاتيح). اختُبر العقد كاملًا مقابل خادم بوابة وهمي يطبّق نفس الترويسات والحقول والتوقيع (`tests/api.test.js`). قبل الإطلاق: أنشئ طلبًا تجريبيًا بمبلغ صغير على مفاتيح Plutu **التجريبية** (الوضع «تجريبي») وتأكد من الدورة كاملة. إن اختلف عنوان الـ API عندك عن الافتراضي `https://api.plutus.ly/api/v1` فعدّله من نفس النموذج. ضع رابط الـ Webhook (يظهر في بطاقة البوابة) في لوحة Plutu إن طلبت ذلك.

## النوع 2: بوابة عامة عبر API (أي مزوّد)

لأي مزوّد يوفّر «إنشاء دفعة ← رابط دفع». تحدّد من الإدارة:

1. **عنوان إنشاء الدفعة** (https) وصيغة الطلب (JSON أو Form).
2. **الترويسات** (JSON)، مثلًا `{"Authorization": "Bearer {{api_key}}"}`.
3. **قالب الطلب** (JSON) بمتغيرات:
   `{{amount}}` (د.ل بثلاث خانات) · `{{amount_minor}}` (بالدرهم 1/1000) · `{{currency}}` · `{{order_number}}` · `{{payment_ref}}` · `{{return_url}}` · `{{cancel_url}}` · `{{webhook_url}}` · `{{customer_name}}` · `{{customer_phone}}` · `{{customer_phone_local}}` · `{{description}}` · `{{api_key}}` · `{{api_secret}}`.
   أضف `:number` لإرسال رقم بدل نص: `"amount": "{{amount:number}}"`.
4. **مسار رابط الدفع ومرجع العملية** في الرد، مثل `data.checkout_url` و`data.id`.
5. (اختياري لكن موصى به) **عنوان الاستعلام عن الحالة** مع `{{provider_ref}}` ومسار الحالة وقيم «مدفوع/فشل/ملغي». عند عودة العميل يسأل الخادم البوابة مباشرة.
6. **Webhook موقَّع**: اسم ترويسة التوقيع، الخوارزمية (SHA‑256/512)، الترميز (hex/base64)، ومسارات المرجع والحالة ومعرّف الحدث والمبلغ. أدخل **Webhook Secret**؛ بدونه تُرفض كل الإشعارات.

مثال (مزوّد افتراضي):

```json
// الترويسات
{"Authorization": "Bearer {{api_key}}", "Content-Type": "application/json"}
// قالب الطلب
{"amount": "{{amount:number}}", "currency": "{{currency}}", "reference": "{{payment_ref}}",
 "return_url": "{{return_url}}", "callback_url": "{{webhook_url}}"}
// مسار رابط الدفع: data.checkout_url   — مرجع العملية: data.id
```

غير مدعوم: بوابات تعمل بسكربت صندوق منبثق في المتصفح (مثل Lightbox لدى Moamalat)، لأنها تتطلب تحميل سكربت خارجي في صفحة الدفع. إن كانت هذه بوابتك فيلزم محوّل مخصّص (ملف في `server/payments/providers/` + تسجيله في `registry.js`).

## بوابة الاختبار (للتطوير فقط)

نوع `sandbox` يظهر في الإدارة فقط عند `NODE_ENV≠production` و`PAYMENT_SANDBOX=1`. لا يمكن وجوده في متجر حي.

## إضافة محوّل جديد (للمطوّر)

ملف في `server/payments/providers/<name>.js` يصدّر كائنًا فيه `type`, `label`, `description`, `fields` (تعرّف نموذج الإدارة تلقائيًا) و`createPayment`، واختياريًا `fetchStatus` و`parseReturn` و`parseWebhook` (ترمي خطأ إن كان التوقيع غير صالح وتعيد `{eventId, providerRef | paymentRef, status: 'paid'|'failed'|'cancelled', amount (بالدرهم)}`). سجّله في `registry.js`.
