# استضافة PHP/Node.js — دليل كامل

هذا المجلد هو كل ما يحتاجه خادم (VPS) منفصل عن Supabase، لتشغيل المواقع التي
يولّدها الذكاء الاصطناعي بلغة PHP أو Node.js حقيقية (متجر إلكتروني وعيادة
بلغة PHP، شركة ومعرض أعمال بلغة Node.js)، كل موقع في Docker container معزول
خاص به، مع شهادة HTTPS تلقائية لكل عميل.

الصفحة التعريفية ومنيو المطعم **لا علاقة لها بهذا المجلد** — تبقى تُنشر على
Cloudflare Workers كما كانت تماماً، بلا أي تغيير.

## الفكرة في جملتين

عميلك يصف نشاطه كالعادة بالضبط، بلا أي خيار جديد يظهر له. الذكاء الاصطناعي
يختار PHP أو Node.js تلقائياً حسب نوع الموقع، يكتب مشروعاً كاملاً، ثم
Supabase يرسله لهذا الخادم الذي يبنيه ويشغّله وينشره — تلقائياً، بلا ضغط زر
إضافي من أي طرف.

## الإعداد (مرة واحدة فقط)

على خادم VPS (Ubuntu 22.04/24.04 أو Debian 12 موصى به)، بعد نسخ هذا المستودع
إليه (`git clone` أو `rsync`):

```bash
sudo bash infra/vps-setup.sh
```

هذا الأمر الواحد يُنصّب ويُشغّل كل شيء (Docker، Caddy، Node.js، الحماية
الأساسية، خدمة النشر) ويطبع في النهاية المفتاح السري الذي تحتاج نسخه إلى
Supabase مرة واحدة (راجع `docs/SUPABASE_DEPLOY.md` القسم 6). السكربت أمِن
لإعادة التشغيل — لن يولّد مفتاحاً جديداً إن كان موجوداً، ولن يعطّل أي موقع
يعمل بالفعل.

**المتطلب الوحيد بعد ذلك**: سجل DNS واحد: `*.apps.ibtkar.ly` (أو النطاق الذي
تختاره) يشير لعنوان IP هذا الخادم.

## البنية المعمارية

```
Supabase (ai-gateway) --يكتب-> websites.config.files (JSON لمسارات/محتوى الملفات)
       |
       v  (deploy-vps edge function، بنفس توكن المستخدم نفسه)
   HTTPS + Bearer DEPLOY_AGENT_SECRET
       |
       v
[deploy-agent على الـVPS]
   1. يتحقق من كل ملف (مسارات، حجم، نقطة الدخول، بلا سكربتات تنصيب خبيثة)
   2. يبني صورة Docker مخصّصة لهذا الموقع فقط (Dockerfile ثابت يتحكم به
      النظام، الذكاء الاصطناعي لا يكتبه أبداً)
   3. يُشغّل container معزول تماماً: read-only، صلاحيات نظام محذوفة بالكامل
      إلا الضروري، حدود ذاكرة/معالج/عمليات صارمة، مستخدم غير root
   4. يفحص صحته (health check) قبل أي تبديل
   5. يسجّل مساراً في Caddy (بروكسي عكسي + شهادة HTTPS تلقائية لكل نطاق فرعي)
   6. يحذف النسخة القديمة فقط بعد تأكد نجاح الجديدة (صفر توقف)
       |
       v
https://<slug>.apps.ibtkar.ly  <-- يعمل فوراً، شهادة SSL صالحة تلقائياً
```

كل موقع له أيضاً قاعدة بيانات SQLite خاصة به (مجلد بيانات معزول Docker
volume)، تبقى عبر كل إعادة نشر، ولا يراها أي موقع آخر.

## الأمان بالتفصيل (كل نقطة هنا مُختبَرة فعلياً، لا نظرية فقط)

- **عزل كامل بين المواقع**: كل موقع في container منفصل، شبكة بيانات منفصلة،
  صلاحيات نظام محذوفة بالكامل (`--cap-drop ALL`) إلا ما يحتاجه PHP حرفياً
  ليبدأ (SETUID/SETGID لخفض صلاحياته من root إلى www-data — تم التحقق أن
  حذفها بالكامل كان يُبقي عمليات PHP تعمل كـ`root` فعلياً، وهذا أُصلح).
- **نظام ملفات للقراءة فقط** (`--read-only`) — الكتابة الوحيدة المسموحة هي
  مجلد البيانات الخاص بالموقع (`/data`، قاعدة SQLite).
- **حدود صارمة للموارد**: ذاكرة 256MB، نصف معالج، 128 عملية كحد أقصى لكل
  موقع — موقع واحد معطوب لا يمكنه إسقاط الخادم.
- **لا تحكّم للذكاء الاصطناعي بالبنية التحتية**: الـDockerfile ثابت يكتبه
  النظام فقط (`templates/Dockerfile.php`, `templates/Dockerfile.node`)، لا
  يراه الذكاء الاصطناعي ولا يُسمح له بكتابة أي ملف بنية (Dockerfile،
  docker-compose، nginx.conf، .htaccess) — كل هذا يُرفض صراحةً في التحقق.
- **تحقّق مزدوج مستقل**: `ai-gateway` (Supabase) يتحقق من مخرجات الذكاء
  الاصطناعي أولاً، و`deploy-agent` (الخادم) يتحقق منها مرة أخرى بشكل مستقل
  تماماً قبل أن تلمس Docker — لا طرف يثق بالآخر.
- **حماية من اختراق المسارات (path traversal)**: أي مسار فيه `..` أو يبدأ
  بـ`/` أو يحاول الخروج من مجلد المشروع يُرفض فوراً.
- **قاعدة بيانات SQLite فقط، بلا شبكة**: لا اتصال خارجي، لا بيانات اعتماد
  قاعدة بيانات مشتركة بين المواقع.
- **المفتاح السري بين Supabase والخادم** (`DEPLOY_AGENT_SECRET`) يُقارَن
  بمقارنة ثابتة الزمن (`crypto.timingSafeEqual`) لمنع هجمات توقيت المقارنة.
- **واجهة Caddy الإدارية** محصورة على `127.0.0.1` فقط، لا تصل من الإنترنت
  إطلاقاً.
- **استعادة تلقائية بعد إعادة تشغيل الخادم**: Caddy يستعيد مساراته تلقائياً
  (`--resume`)، وخدمة النشر أيضاً تعيد بناء كل المسارات من واقع الحاويات
  الفعلية العاملة إن احتاج الأمر — لا يختفي موقع عميل صامتاً بعد إعادة تشغيل.

### الخطر المتبقي الذي لم نُغلقه بالكامل، وبصراحة

فحص SSRF/DNS rebinding على مستوى الشبكة بين الحاويات نفسها لم يُضَف هنا
(غير ضروري لأن المواقع لا تتصل بأي شبكة خارجية أصلاً حسب تعليمات الذكاء
الاصطناعي)، لكن لم نقيّد خروج الإنترنت (egress) من الحاويات بجدار حماية على
مستوى الشبكة — الاعتماد حالياً على أن تعليمات الذكاء الاصطناعي تمنع أي طلب
شبكة خارجي، وعلى التحقق من المخرجات. لتشديد أكثر مستقبلاً: قاعدة جدار حماية
(iptables/nftables) تمنع كل الحاويات من الوصول لأي شيء خارج 127.0.0.1 والشبكة
العامة المطلوبة فقط.

## مجلد deploy-agent

خدمة Node.js/Express صغيرة (راجع `deploy-agent/server.js`)، مُختبَرة فعلياً
في بيئة Docker حقيقية (نشر PHP، نشر Node، إعادة نشر بلا حاويات متبقية، حذف،
رفض كل حالات الاختراق المذكورة أعلاه) قبل تسليمها. الملفات:

- `server.js` — الـEndpoints (`/deploy`, `/remove`, `/health`) + المصادقة.
- `validate.js` — كل قواعد التحقق من مشروع الذكاء الاصطناعي.
- `deploy.js` — تنسيق البناء/التشغيل/التنظيف (zero-downtime).
- `docker.js` — غلاف حول أوامر `docker` (بدون أي shell، كل الاستدعاءات
  بمصفوفة وسائط لمنع حقن الأوامر).
- `caddy.js` — التحدث مع واجهة Caddy الإدارية لتسجيل/حذف مسار كل موقع.
- `templates/Dockerfile.{php,node}` — صور النظام الثابتة لكل لغة.

## ماذا لو لم يكن لديك VPS بعد؟

كل شيء في Supabase (الـmigrations، دالة `deploy-vps`، تعليمات الذكاء
الاصطناعي) يعمل ويُنشر بأمان حتى بدون خادم — فقط محاولة النشر التلقائي
ستفشل بصمت برسالة "vps_not_configured" (الموقع يبقى محفوظاً بحالة "مسودة"،
بلا أي كسر). عندما يصبح الخادم جاهزاً، شغّل `vps-setup.sh` وأضف الأسرار في
Supabase، وستبدأ كل المواقع الجديدة والقديمة (عند إعادة بنائها) بالنشر فوراً.
